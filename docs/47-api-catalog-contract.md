# 47 — The API Describes Itself (Sprint 28)

> Spec §77 lists **API Marketplace** among the Phase 4 items. This is the part
> of it that has content today, and the part that does not is refused with the
> reason.

## 1. What an "API marketplace" can honestly mean here

A marketplace of third-party integrations is a directory. Directories are worth
building when there is something to list; there are no third-party integrations
to this platform, so a marketplace of them would be an empty room with a sign on
it — the same reasoning §48 used to decline a roster of AI agents with no jobs.

What an integrator actually lacks is narrower and real: **the API does not
describe itself.** `docs/30` says what the public API offers, and a human has to
find it, read it, and trust that it still matches the code. Everything else
about integration is machine-readable — keys, webhooks, signatures — and the
one thing you would build a client from is prose.

So this sprint publishes a catalogue: the public endpoints, the scopes that gate
them, the events a webhook can subscribe to, and the limits, at a public URL, in
JSON.

## 2. It is generated, never maintained

The catalogue is built **from the running application** — the router's own
registry for endpoints, the shared `EVENTS` catalog for events, the scope
constants for scopes. Nothing in it is a list somebody has to remember to
update.

This is not tidiness. A hand-maintained API description drifts, and a drifted
description is worse than none: it is a document that looks authoritative while
telling an integrator to call something that no longer exists. This codebase has
already been bitten by exactly that shape — a pre-commit guard registered so it
never ran, and an isolation probe counting rows that did not exist. Both looked
like they worked.

A test asserts the catalogue matches the router, so adding a public endpoint
without it appearing is a failing build rather than a stale document.

## 3. What it contains

```
GET /api/v1/public/v1/catalog        (public — an integrator has no key yet)

{
  version, generatedAt,
  authentication: { scheme, header, keyPrefix },
  rateLimit:      { requests, windowSeconds, headers },
  endpoints: [{ method, path, scope }],
  events:    [{ name, description }],
  scopes:    [...],
  webhooks:  { signature, header, retries },
  refuses:   [...]
}
```

`refuses` is deliberate: it names what this API does **not** do — no health
data, no cross-tenant reads, no payment execution — because an integrator
planning around a capability that will never arrive has wasted their time, and
they cannot tell the difference between "not built yet" and "never" from a list
of endpoints.

Publicly readable, because an integrator evaluating whether to build has no API
key yet, and requiring one to find out what the API does is a door with the
instructions on the inside.

## 4. What it is not

- **Not OpenAPI.** A hand-shaped subset of OpenAPI is not OpenAPI, and tools
  that consume it would break on the parts we did not implement. If a real
  OpenAPI document is wanted it should be generated by a decorator-driven
  toolchain (`@nestjs/swagger`), which is a larger commitment than this sprint.
  The catalogue says what it is: a description, not a specification.
- **Not a client SDK.** Generating clients from a description we just admitted
  is not OpenAPI would be building on sand.
- **Not an app directory, install flow, or third-party publishing.** See §1.
